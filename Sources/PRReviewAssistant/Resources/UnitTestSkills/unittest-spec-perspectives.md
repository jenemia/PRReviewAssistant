# spec 기반 UnitTest 케이스 도출 (여러 관점)

## 읽을 문서
- 대상 spec 폴더의 `spec.md`와 같은 폴더의 `qa.md`를 함께 읽는다. 앱이 넘긴 발췌가 잘렸으면 "생략한 섹션" 목록을 보고 필요한 섹션을 파일에서 직접 읽는다.
- 기대값의 출처 우선순위: qa.md 시나리오의 기대 결과 → spec.md 수용 기준·규칙 → 브랜치 diff의 의도. 구현을 실행해 나온 값은 기대값이 아니다.

## 관점별로 따로 훑는다
한 관점에서 케이스를 다 뽑은 뒤 다음 관점으로 넘어간다. 같은 규칙이 여러 관점에서 나오면 하나로 합친다.

| 관점 | 찾을 것 | 예 |
|---|---|---|
| 수용 기준(정상 흐름) | 기능이 끝났다고 말할 조건 | 한 판 종료 시 점수만큼 재화 지급 |
| QA·테스트 시나리오 | qa.md의 시나리오 ID와 기대 결과 | DT-11: 허용 stackable 외 타입 → 거부 |
| 예외·경계 | 0, 1, 상한, 상한+1, 음수, 만료 직전·직후, 중복 요청, 재진입 | 일일 상한 3회째 이후 스폰 안 함 |
| 저장·복원 | 세이브 슬라이스, 마이그레이션, 재접속·시즌 교체 후 값 | 시즌이 바뀌면 이전 시즌 진행값 초기화 |
| 설정·데이터 매핑 | 키, enum, 테이블 값, 서버 응답 → 내부 값 | 테마 키 → 표시 리소스 경로 |

## 케이스 작성
- 케이스마다 근거 섹션이나 시나리오 ID를 테스트 이름이나 주석에 남긴다(예: `// qa.md DT-11`). 사람이 spec과 테스트를 다시 연결할 때 쓴다.
- 결정 로직이 아닌 것(연출, 프리팹 배치, UI 표시)은 케이스로 만들지 않고 "UnitTest 범위 밖"으로 보고한다.
- 기대값이 spec에 숫자로 없으면 경계와 불변식만 검증한다(음수가 아님, 합계가 100%).

## spec과 구현이 다를 때
- spec 기대값으로 테스트를 쓰고, 다른 점을 한두 문장으로 보고한다(앱의 `specMismatch`). 구현에 맞춰 기대값을 바꾸지 않는다.
- 이 경우 테스트는 검증에서 실패하므로 앱은 파일을 쓰지 않고 불일치로 보고한다. 알려진 버그로 실패를 남기려면 사람이 따로 결정한다.
