# UnitTest 대상 선별 기준

## 범위
- 비교 기준은 브랜치의 부모다. `sprint/sNN/...` 브랜치는 `sprint/sNN/main`과 비교한다. PR 제안이 있으면 그 base를 쓴다.
- 이 브랜치가 직접 커밋한 변경만 본다. 다른 브랜치를 병합하면서 들어온 변경은 앱이 먼저 제외한다.
- 파일마다 함께 주는 "이 브랜치 커밋" 메시지로 이 브랜치의 의도를 파악하고, diff에서 실제로 바뀐 동작으로 판단한다.

## 고르는 것: 결정 로직
입력이 정해지면 결과가 정해지는 코드다.

| 종류 | 예 |
|---|---|
| 자격·조건 분기 | 입장 가능, 지급 가능, 해금, 스폰 가능 여부 |
| 수치 계산 | 보상량, 재화 차감, 확률, 남은 횟수, 쿨타임 |
| 기간·시즌 | 시작·종료 경계, 일일·시즌 리셋 |
| 상태 전이 | 라운드 진행, 대기 → 진행 → 종료, 중복 수령 방지 |
| 데이터 변환 | 저장 데이터 이전, enum·키·ID 매핑 |

behavior에는 `진입점: 조건 → 결과` 규칙을 1~4개 쓴다. 기대 결과를 구체적인 값으로 쓸 수 있어야 후보다.

## 제외하는 것
- UI 배치, 연출, 애니메이션, 사운드, 리소스 경로, 프리팹·UI 연결, 표시 문자열.
- 에디터, 치트, 디버그, 생성 코드.
- 선언·이름·포맷·using·주석·로그만 바뀐 코드, 단순 null 검사, 삭제만 있는 변경.
- 동작이 그대로인 리팩터링, 단순 위임, getter/setter, 상수 선언만 있는 파일.
- 기존 테스트가 바뀐 동작을 이미 검증하는 파일.

## Unity 의존 코드
MonoBehaviour이거나 TMPro·UI·싱글톤에 묶여 있어도 결정 로직이 있으면 후보로 반환한다. 생성 단계가 public API를 직접 호출하거나, 안 되면 규칙을 테스트 안에 옮겨(복제) 검증한다.

## 우선순위
- 3: 재화·보상 지급과 차감, 확률, 횟수 상한, 기간·시즌 경계, 저장 데이터 이전. 틀리면 유저 자산이나 진행이 잘못된다.
- 2: 그 밖의 결정 로직과 상태 전이.
- 1: 표시용 계산처럼 영향이 낮은 규칙.
