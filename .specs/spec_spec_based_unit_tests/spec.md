## 목적과 범위

사이드바에 Spec 탭을 추가해 등록 저장소의 spec 문서를 목록으로 보여 주고, 문서 하나를 골라 그 문서의 규칙과 테스트 시나리오를 기대값 기준으로 UnitTest를 생성한다. 지금 UnitTest 생성은 브랜치 diff에서 대상을 고르고, 생성 에이전트가 관련 `.specs` 문서를 스스로 찾아 기대값 참고로만 쓴다. 이 기능은 대상 선정의 기준을 diff 대신 사용자가 고른 spec 문서로 바꾼다. diff가 없어도 되므로 이미 머지된 기능이나 리팩터링 후 회귀 확인에도 쓸 수 있다.

| 포함 | 미포함 |
|---|---|
| Spec 탭(저장소별 spec 목록, 본문 보기, UnitTest 생성 버튼, 직전 결과) | 에이전트가 spec 문서를 새로 작성·수정하는 기능 |
| spec에서 규칙을 뽑고 구현 소스에 연결하는 선별 단계 | spec과 브랜치 diff의 교집합 선정 |
| 기존 생성·검증·반영 파이프라인 재사용 | 커밋·푸시, Unity 런타임 테스트 |
| spec 기준 결과 저장과 규칙별 커버 표시 | 기존 "최근 세션" 하위 spec 목록(Cursor 세션 묶음)과의 통합 |

## 결정

| 항목 | 결정 |
|---|---|
| 결정 — 탭의 의미 | spec 문서를 생성하는 탭이 아니라 spec 목록·선택 탭이다. |
| 결정 — 대상 선정 | spec만으로 선정한다. 브랜치 diff는 쓰지 않는다. |
| 결정 — 작업 브랜치 | 등록 폴더의 현재 브랜치 HEAD를 기준으로 기존 이름 규칙의 `unittest/` 로컬 브랜치에서 작업한다. 커밋·푸시는 하지 않는다. |
| 결정 — 기존 spec 목록 | "최근 세션" 아래 spec 이름 목록은 그대로 두고 Spec 탭과 합치지 않는다. 통합은 후속 검토. |

## 구현부

- **Spec 탭.** `ContentView.swift`의 `SidebarItem`에 `spec` 케이스를 추가하고 사이드바 "UnitTest" 섹션에 "Spec 문서로 생성" 항목을 둔다. 화면은 `Views/SpecUnitTestView.swift`다. 등록 저장소마다 `WorkspaceSpecCatalog.documents(in:)`(`CursorSessionSpecStore.swift`)로 `specs/`·`.specs/` 아래 `spec.md`를 찾아 저장소별로 묶는다. 표시 이름은 폴더 이름이고, 문서 첫 제목과 헤더의 상태·최종 갱신 줄을 읽을 수 있으면 함께 보여 준다(읽지 못하면 생략). 목록은 탭을 열 때와 새로 고침 버튼으로 다시 읽는다.
- **Spec 상세 화면.** 선택한 문서 본문을 `MarkdownContentView`로 렌더링하고, 위쪽에 작업 기준(저장소, 현재 브랜치, 만들 UnitTest 브랜치 이름)과 "UnitTest 생성" 버튼, 진행 메시지, 직전 결과를 둔다. 결과 표시는 브랜치 UnitTest 결과 화면의 파일별 결과·추출 규칙 표시를 `UnitTestFileResultsView`(`BranchRequestView.swift`)로 분리해 함께 쓴다. 같은 저장소에서 브랜치 UnitTest, spec UnitTest, 구현 작업 중 하나가 진행 중이면 `ReviewStore.isUnitTestBlocked(in:)`로 버튼을 막고, 브랜치 UnitTest도 spec UnitTest가 진행 중이면 시작하지 않는다. 작업 공간 신뢰·로그인 요청은 브랜치 모드의 권한 요청(`BranchAgentPermissionRequest.Action.specUnitTest`)을 현재 브랜치 기준으로 재사용한다.
- **작업 기준 브랜치.** 등록 폴더의 현재 로컬 브랜치(`git symbolic-ref --short HEAD`)와 그 HEAD SHA를 기준으로 한다. detached HEAD여서 브랜치 이름을 정할 수 없으면 실행 전에 중단하고 사유를 보여 준다. `unitTestBranchName(for:)`는 `unittest/` 브랜치에 다시 적용해도 같은 이름을 돌려주므로, 현재 브랜치가 이미 UnitTest 브랜치면 그 브랜치에서 이어서 진행한다. 브랜치 전환, stash 보관·재적용, fast-forward·갈라짐 중단, 기존 테스트 보호 규칙은 관련 스펙 구현부를 그대로 따른다.
- **spec 기반 대상 선정.** `UnitTestVerifier.verifySpec`이 diff 수집 대신 다음 순서로 `Candidate`를 만든다. 브랜치 전환부터 생성·검증·반영까지는 브랜치 모드와 공통인 `runOnUnitTestBranch`를 쓴다.
  1. 앱이 등록 폴더 작업 트리의 spec 본문(앞 20,000자)과 spec이 참조한 C# 경로를 모은다. 참조 경로는 본문 백틱 안의 `.cs` 경로 또는 파일 이름을 기준 SHA의 추적 파일(`git ls-files '*.cs'`, 테스트 경로 제외)과 대조해 확정한다.
  2. 새 에이전트 호출(`CursorAgent.selectSpecUnitTestTargets`)이 spec의 `구현부`·`테스트 시나리오`에서 `진입점: 조건 → 결과` 규칙을 뽑고, 각 규칙을 구현한 소스 경로를 반환한다. 후보는 1의 참조 경로를 우선하고, 그 밖의 경로는 추적 C# 파일 목록에 있을 때만 받는다(앱 검증). 목록에 없는 경로, 테스트 경로, 범위 밖 판정은 제외하고 집계한다.
  3. 소스별로 규칙을 묶어 기존 중요도·최대 5개 상한을 적용한다. 규칙을 하나도 뽑지 못하면 "규칙 부족"으로 보고하고 생성하지 않는다.
  분류 응답이 유효하지 않으면 기존처럼 생성을 중단한다.
- **생성 요청.** 기존 `generateUnitTest`를 재사용하되 `Target.spec`이 있으면 spec 모드 요청에는 diff 대신 대상 소스 전문, 선택한 spec 경로, 해당 소스에 연결된 규칙을 넣는다. 프롬프트는 "에이전트가 관련 spec을 찾는다" 대신 "지정한 spec 문서가 기대값의 1순위 근거"라고 명시하고, spec과 구현이 다르면 spec 기대값으로 테스트를 쓰되 `reason`에 불일치를 적게 한다. 규칙 출처(spec/diff/code) 표시, 원본 직접 호출·원본 로직 복제, Unity 대체 소스, 경로 정책은 그대로다.
- **검증과 불일치 구분.** 검증 실패 시 기존 재시도 정책을 따른다. 재시도 후에도 실패하고 에이전트가 제안의 `specMismatch`로 불일치를 보고한 파일은 `FileResult.Status.specMismatch`("spec과 구현 불일치")로 표시하고 쓰지 않는다. 불일치가 있으면 결과는 실패로 본다. 생성 오류·컴파일 실패와는 다른 상태로 집계한다.
- **결과 저장.** `PersistedState.specUnitTestResults`(키: 저장소 id + spec 상대 경로, `ReviewStore.specUnitTestID`)를 추가해 `UnitTestVerification`을 저장한다. 기존 `branchUnitTestResults`와 섞지 않는다. 결과 요약에는 기준 브랜치·SHA, spec 경로, 추출 규칙 수, 테스트로 다룬 규칙 수, 건너뛴 규칙 수(Unity 의존, 상한 초과, 불일치)를 보여 준다.

## 사이드 이펙트

| 항목 | 영향과 완화 |
|---|---|
| 사이드 이펙트 — 등록 폴더 브랜치 전환 | 브랜치 모드와 같이 등록 폴더가 `unittest/` 로컬 브랜치로 바뀐다. Unity 에디터가 다시 가져오기를 할 수 있다. 상세 화면에 만들 브랜치 이름을 실행 전에 보여 주고, stash 규칙은 기존과 같다. |
| 사이드 이펙트 — spec 품질 의존 | 테스트 시나리오가 없거나 서술이 모호한 spec은 규칙이 적거나 틀릴 수 있다. 규칙 부족이면 생성하지 않고, 추출한 규칙을 결과에 그대로 보여 사용자가 검토하게 한다. |
| 사이드 이펙트 — spec과 구현 불일치 | 기대값을 spec에서 가져오므로 오래된 spec은 실패 테스트를 만든다. 실패 파일은 쓰지 않고 "spec과 구현 불일치"로 구분해 spec 갱신 또는 버그 확인의 단서로 쓴다. |
| 사이드 이펙트 — 대상 경로 오인 | 에이전트가 spec에 없는 파일을 고를 수 있다. 추적 C# 파일 목록 밖 경로는 버리고, 참조 경로를 우선한다. |
| 사이드 이펙트 — 입력 크기 | spec 본문과 소스 전문이 커질 수 있다. spec 본문·소스당 입력을 제한하고 잘렸으면 결과에 표시한다. |
| 사이드 이펙트 — 기존 브랜치 UnitTest | `UnitTestVerifier.verify`에 모드가 추가되므로 브랜치 모드 동작이 바뀌면 안 된다. 기존 테스트(`UnitTestVerifierTests`)를 그대로 통과시키고 spec 모드 테스트를 따로 둔다. |
| 사이드 이펙트 — 저장 데이터 | 새 저장 키를 추가하므로 이전 버전 저장 파일은 키가 없어도 빈 값으로 읽혀야 한다(`decodeIfPresent`). |
| 사이드 이펙트 — 사이드바 spec 이름 중복 | "최근 세션" 아래 spec 목록과 이름이 겹쳐 보일 수 있다. 섹션 제목과 아이콘으로 구분하고 통합은 후속으로 둔다. |

## 테스트 시나리오

| 항목 | 상황 | 기대 결과 |
|---|---|---|
| 테스트 — Spec 탭 목록 | 등록 저장소 두 곳에 `.specs/*/spec.md`가 있음 | 저장소별로 묶여 표시되고, 선택하면 본문이 렌더링된다. |
| 테스트 — Spec 탭 빈 상태 | spec 문서가 없는 저장소 | 빈 상태 안내가 보이고 생성 버튼이 없다. |
| 테스트 — spec 참조 경로 확정 | spec 본문에 백틱 `.cs` 경로와 파일 이름이 있음 | 추적 파일에 있는 경로만 참조 경로로 확정되고 테스트 경로는 빠진다. |
| 테스트 — spec 기반 대상 선정 | 에이전트가 참조 경로 하나와 목록 밖 경로 하나를 반환 | 목록 밖 경로는 제외 집계되고 참조 경로만 생성 대상이 된다. |
| 테스트 — 규칙 부족 | 테스트 시나리오와 규칙이 없는 spec | 생성하지 않고 "규칙 부족"으로 보고한다. 브랜치 전환도 하지 않는다. |
| 테스트 — 생성 요청에 spec 지정 | spec 모드 생성 요청 | 프롬프트에 선택한 spec 경로, 연결된 규칙, 소스 전문이 들어가고 diff는 없다. |
| 테스트 — spec 모드 작업 브랜치 | 등록 폴더가 `sprint/s29/feature/x`에 있고 깨끗함 | `sprint/s29/unittest/x`로 전환되고 통과한 테스트가 커밋 없이 남는다. |
| 테스트 — detached HEAD 중단 | 등록 폴더가 detached HEAD | 실행 전에 사유를 보여 주고 중단한다. |
| 테스트 — spec과 구현 불일치 | spec 기대값과 구현 결과가 달라 재시도 후에도 실패 | 파일은 쓰이지 않고 "spec과 구현 불일치"로 표시된다. |
| 테스트 — 동시 실행 차단 | 같은 저장소에서 브랜치 UnitTest가 진행 중 | spec 생성 버튼이 비활성화된다. |
| 테스트 — 결과 저장 | 생성 후 앱 재시작 | 해당 spec의 직전 결과가 다시 보인다. 이전 버전 저장 파일도 오류 없이 읽힌다. |
| 테스트 — 브랜치 모드 회귀 | 기존 브랜치 선택·검증 실행 | 기존 동작과 결과가 같고 기존 UnitTest 테스트가 모두 통과한다. |

## 미결

- 개발: 구현부 범위의 남은 작업 없음. 현재 브랜치가 `unittest/` 브랜치인 경우는 이름 규칙이 같은 이름을 돌려줘 그대로 이어서 진행한다. spec 본문 상한은 20,000자, 소스는 기존 상한(40,000자)이다.
- 기획: 범위 밖 추가 작업 없음.
- QA: 실제 Unity 저장소의 spec 하나로 규칙 추출, 대상 연결, 생성·검증 결과를 확인한다.
